# QDM 0.1.1：移除固定轮询造成的吞吐限制

## 问题与结论

用户报告公网 TLS 下载：4 路约 2 MB/s，8 路约 4 MB/s，64 路约 32 MB/s，浏览器约 50 MB/s。本次未重新下载用户的 CDN 安装包，也未把公网速度差归因于 CDN。

检查代码发现 0.1.0 每 20 ms 调用一次 curl_multi_perform；数据就绪不会直接唤醒下载引擎。某些 TLS 收包路径在下一轮调度前无法继续处理，因此增加并发会掩盖每路接收受限的问题。这个周期不是所有网络环境下都能用固定公式换算的带宽上限，必须通过对照验证。

本机 TLS 对照确认了该调度方式的性能代价。0.1.1 改用事件驱动后，4 路已达到该本机测试环境的约 135 MiB/s，增加到 8/16/64 路不再获得类似线性收益。

## 代码变更

- CURLMOPT_SOCKETFUNCTION 注册 Qt 5.8 的读/写 QSocketNotifier，socket 就绪时调用 curl_multi_socket_action。
- CURLMOPT_TIMERFUNCTION 控制独立单次 Qt 精确定时器；0 ms 也延迟到事件循环，避免重入。
- 100 ms 心跳只处理状态、重试、UI 和检查点，不再轮询网络。
- Windows SOCKET 捕获为原始指针宽度类型，忽略 Qt 5.8 激活信号中的 int 句柄参数。
- socket 移除时先禁用并断开 notifier，再 deleteLater；通过 serial 过滤句柄数值复用后的旧事件。
- 保留同步写入、SHA-256、FlushFileBuffers、SQLite FULL 和证书链/主机名校验。本次没有通过减少恢复保护或关闭 TLS 验证换取速度。
- 增加可选 --ca-file，用于显式信任私有/本机测试 CA；不修改系统信任。
- 提供隔离的 baseline/optimized 构建目录，以便旧实例继续运行时构建新版。

## 吞吐对照

环境：同机 Windows x64、Qt 5.8/v120 Release、相同官方 libcurl DLL；本机 Python TLS HTTP/1.1 服务、1 GiB 有确定内容的资源、实际磁盘写入、哈希和检查点。每次运行约 5 秒，采用第 1 秒以后的事件时间差和字节差，单位为 MiB/s。

| 配置 | 旧版固定轮询 | 事件驱动 |
| --- | ---: | ---: |
| 4 路 | 21.82 | 135.44 |
| 8 路 | 43.08 | 135.06 |
| 16 路 | 79.98 | 131.66 |
| 64 路 | 101.41 | 130.26 |

原始记录：

- `tests/work/benchmark-611d269460/results.json`：旧驱动，基线构建仅增加了测试 CA 入口，未改变原调度方式。
- `tests/work/benchmark-d596e36c25/results.json`：新驱动，协议和落盘策略相同。
- `docs/性能对照.json`：精简归档，包含 EXE 摘要与数值，避免依赖被清理的工作目录。

baseline 是变更前准备的隔离构建目录名，不是源码回滚功能。当前源码已全部更新为 0.1.1，再执行 build.cmd baseline 也会编译当前源码；原始对照应以此处归档的 EXE 摘要和测试记录为准。

这是短时诊断对照，不是经过多轮随机顺序、置信区间统计的公开性能评测。本地服务器、磁盘缓存、后台负载和 TLS 实现均会影响数值；不能将本机结果解释为公网能达到相同速度。用户原 CDN 的实际提升仍需在完整有效地址和相同网络条件下复测。

## 正确性验证

0.1.1 的原 18 项集成回归全部通过，目录 `tests/work/0b15b55740`。包括实际 64 段、512 MiB 文件摘要、暂停恢复、强制终止、损坏检查点、ETag 改变、Range 回退及发布恢复。

额外 TLS 完整下载：`tests/work/benchmark-ae8f1f007d`。

- 不传临时测试 CA：不受信任证书被拒绝，未发布最终文件。
- 显式传入测试 CA：512 MiB + 317 byte 文件，4 路、64 路完整下载 SHA-256 均正确。
- 此次完整 TLS 运行的采样吞吐分别约 136.60、132.94 MiB/s，仅作为额外诊断数据。

## 当前限制

网络接收不再等待固定轮询，但文件写入、哈希和刷盘仍在同一个工作线程。慢磁盘、频繁随机写及长时间恢复校验仍可能成为下一阶段瓶颈。后续拆分写线程时必须保留有界队列、反压、取消屏障和先落盘后提交检查点的顺序。

0.1.1 最初只输出到 `build/optimized/bin/QDM.exe`，旧 release 进程继续驻留时，单实例机制可能把新版启动动作转给旧版，造成用户以为已经切换。

0.1.2 已修正该交互，并在旧实例正常退出后同步更新 release/optimized 两个入口。窗口标题与状态栏显示版本，版本冲突时明确提示。实际观察到当前窗口显示 `QDM · 下载管理器 0.1.2`，状态栏为事件驱动下载。单实例、PID/版本/路径记录和暂停保存测试通过，记录位于 `tests/work/010e909ff0/instance`。本次没有重新测量用户 CDN 的实际下载速度。
